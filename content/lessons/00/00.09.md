Engineering work is a chain of decisions, and you need to know which version of a calculation produced which drawing. Git solves that with one idea: name every file and every snapshot by a hash of its content. In this lesson you build that idea yourself in about 30 lines, then see why it makes history tamper-evident and bugs findable in a handful of steps.

## A hash is a fingerprint

A cryptographic hash function maps any sequence of bytes to a fixed-size number, 160 bits for SHA-1 as used by classic git. Two properties matter:

1. The same content always gives the same hash.
2. Changing a single byte changes the hash completely and unpredictably.

Git names a file's content ("blob") by

$$
\text{id} = \operatorname{SHA1}\big(\texttt{"blob "} \,\|\, \text{length} \,\|\, \texttt{\textbackslash 0} \,\|\, \text{content}\big).
$$

A directory ("tree") is a list of names and the ids of what they contain, hashed in turn. A commit is a hash of a tree id, the parent commit id, the author and the message. So a commit id is a hash of hashes all the way down: change any byte of any file in history and every id after it changes.

## How unlikely is a collision?

With $n$ objects and a $b$-bit hash, the birthday bound gives the probability that any two collide:

$$
p \approx \frac{n^2}{2^{\,b+1}} .
$$

For a million files and $b = 160$, $p \approx 10^{12}/2^{161} = 3.4\times10^{-37}$. Accidental collisions are not a practical concern. Deliberate SHA-1 collisions have been shown, which is why git is moving to SHA-256; the idea stays the same.

## Finding the commit that broke something

If a test passed at commit 0 and fails at commit $N$, `git bisect` checks the middle, keeps the half that contains the change, and repeats. It's the bisection method you'll meet again in lesson 01.02, applied to history, and it needs only

$$
\lceil \log_2 N \rceil
$$

test runs. A thousand commits take ten.

:::example The id of a file containing "hello"
Compute the git blob id of a file whose content is the six bytes `hello` plus a newline.

1. Header: `blob 6` followed by a zero byte.
2. Hash the header plus content with SHA-1.
3. Result: `ce013625030ba8dba906f756967f9e9ca394464a`.

Run `echo hello | git hash-object --stdin` in any terminal and you get the same 40 hex digits. Your 30 lines and git agree because they implement the same definition.
:::

```python file=tiny_git.py
"""A content-addressed object store that names blobs exactly like git does."""
import hashlib
import math
import os
import tempfile
import zlib


def blob_id(content: bytes) -> str:
    header = b"blob %d\0" % len(content)
    return hashlib.sha1(header + content).hexdigest()


class Store:
    def __init__(self, root):
        self.root = root

    def _path(self, oid):
        return os.path.join(self.root, oid[:2], oid[2:])

    def put(self, content: bytes) -> str:
        oid = blob_id(content)
        path = self._path(oid)
        if not os.path.exists(path):              # same content is stored once
            os.makedirs(os.path.dirname(path), exist_ok=True)
            with open(path, "wb") as f:
                f.write(zlib.compress(b"blob %d\0" % len(content) + content))
        return oid

    def get(self, oid) -> bytes:
        with open(self._path(oid), "rb") as f:
            raw = zlib.decompress(f.read())
        content = raw[raw.index(b"\0") + 1:]
        assert blob_id(content) == oid, "object corrupted"
        return content


if __name__ == "__main__":
    assert blob_id(b"hello\n") == "ce013625030ba8dba906f756967f9e9ca394464a"
    assert blob_id(b"") == "e69de29bb2d1d6434b8b29ae775ad8c2e48c5391"
    with tempfile.TemporaryDirectory() as d:
        s = Store(d)
        a = s.put(b"E = 210e9  # steel, Pa\n")
        b = s.put(b"E = 210e9  # steel, Pa\n")
        c = s.put(b"E = 210e9  # steel, Pa \n")   # one extra space
        assert a == b and a != c
        assert s.get(a) == b"E = 210e9  # steel, Pa\n"
        print("ids:", a[:10], c[:10])
    p = (1e6) ** 2 / 2 ** 161
    assert 3.4e-37 < p < 3.5e-37
    assert math.ceil(math.log2(1000)) == 10
    print(f"collision chance for 1e6 objects: {p:.2e}")
```

The store writes objects in the same compressed format and folder layout git uses under `.git/objects`. Point it at a real repository and `get` can read git's own blobs.

:::exercise Bisect a regression
Your beam solver's test passed in March and fails today, 600 commits later. Each test run takes 4 minutes. Roughly how long does a bisect take, compared with testing every commit?
---solution---
1. Number of runs: $\lceil \log_2 600 \rceil = 10$, since $2^9 = 512 < 600 \le 1024 = 2^{10}$.
2. Bisect time: $10 \times 4 = 40$ minutes.
3. Testing every commit: up to $600 \times 4 = 2400$ minutes, 40 hours.
4. Bisect is 60 times faster here, and the advantage grows with history length.
:::
